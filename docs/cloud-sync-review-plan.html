    痛点

    1. 记录只在一台 Mac 上，手机看不到。（用户原话）
    2. 记录是流水账，没有按单词、句型、语法整理。（用户原话）
    3. 手机上没有顺手的翻译和纠错工具。（用户原话）
    4. 没有复习计划。一个词查了 8 次，说明“查了也没记住”。推断
    5. 段落级记录多半是工作文本，不适合直接做复习材料。推断

    2. 目标与非目标

    7 个目标，每个都有可验收的指标。

    #目标衡量方式
    G1手机上随手翻译、纠错打开小程序到看到结果 ≤ 3 步；首字 ≤ 2 秒 待实测
    G2多端同步：任一端的记录在另一端可见联网时，写入后 1 分钟内另一端可见
    G3AI 复习材料：每天自动生成每天 06:00 前生成前一天的材料；失败时发告警
    G4按遗忘曲线复习每日复习 ≤ 10 分钟；30 天记忆保持率 ≥ 85%
    G5同步服务故障不影响 CLI服务端宕机时，CLI 照常直连 DeepSeek 翻译；恢复后自动补传
    G6简约的交互打开小程序即可输入；开始复习 ≤ 2 次点击
    G7账号体系：多人使用时数据互相隔离任一接口都读不到其他账号的数据（有自动化测试）

    • 公开注册与商业化（先邀请制）。
    • 小程序正式发布（先用体验版自用）。
    • 完整复刻 Anki（自定义卡组、插件、模板编辑）。
    • 离线翻译（模型在云端，断网时只能看已有记录）。

    4. 小程序翻译与纠错

    小程序提供 CLI 的全部查询能力。AI 调用经过自己的服务端，DeepSeek key 不出服务器。

    CLI 能力在小程序上的对应

    CLI 能力小程序对应说明
    直接输入即翻译（自动判断方向）“翻译” tab：中文 → 英文；其他外语 → 中文方向由规则判断，用户不用选
    /check 纠错独立的“纠错” tab修改处用删除线 + 高亮标出
    单词查询 + 美式音标自动识别单个单词结果第一行是“单词 + 音标”
    /mode s|d不提供；翻译页固定简洁模式详细讲解交给每日材料，翻译页保持简单
    /lang en|zh设置页“解释语言”设置两端同步
    /say朗读按钮服务端生成 mp3，两端共用缓存
    /history“我的 → 记录”包含 CLI 和手机两端的记录
    /notes每日材料由 AI 管线生成
    /quiz“复习” tabFSRS 调度替代随机抽题

    翻译页只保留输入框和结果。语音输入是输入框里的麦克风图标；清空用输入框里的 ✕。不设“加入复习”按钮：每条查询都会进入第二天的材料，查过多次的单元自动加权。

    翻译方向规则

    方向由客户端规则判断，不交给模型，也不让用户选。

    输入判定译成
    含汉字，不含假名和谚文（包括中英混排）中文英文（默认方向）
    单个英文单词外语中文，并附美式音标
    其他外语：英文句子、日文、韩文、法文等外语中文
    要改代码：现在的 detectSourceLang() 见到汉字就判为中文（src/utils/detect.js:34）。日文常含汉字，系统会把它译成英文。改法：先查假名和谚文，有就判为外语。prompt 里“源语言是英文”的规则也改成“源语言是外语”（src/prompts.js:42）。改动放在 packages/core，CLI 同时受益。纯汉字的短日文仍会判成中文，用户点方向标签即可纠正。

    一次翻译请求的链路

    关键设计

    1. prompt 只有一份。把 src/prompts.js 和 src/utils/detect.js 抽到共享包 packages/core，CLI 和服务端都引用它。否则两端会各改各的。例如 ad62460 的“固定翻译方向”修复就得做两遍。
    2. 纠错 prompt 要小改。详细模式现在先分析、后给修改句（src/prompts.js:158）。改成“修改后的句子单独放第一行”，与翻译详细模式一致（src/prompts.js:95）。这样客户端能稳定取出修改句做差异高亮，/say 也能直接读第一行。
    3. 流式输出。小程序用 wx.request 的 enableChunked 和 onChunkReceived 接收分块。待实测 分块按字节切，可能切断一个中文字符，所以要先拼接字节再按 UTF-8 解码。推断 花了知多少没有用过流式请求，这部分没有现成代码。
    4. 首字延迟单独测。花了知多少的 p50 3.5 秒是带推理的记账解析数据，不能直接套用。翻译接口要实测首字时间；如果推理拖慢首字，交互接口就关闭推理或换模型。
    5. 保护 API key 和额度。每个请求带账号令牌。按账号限流：每分钟 20 次、每天 200 次（D13）。输入上限 2000 字符。每个账号另有每日 token 预算。
    6. 每次查询都是一条原始记录。手机查询写入 source = mp，和 CLI 的记录一起进入第二天的材料。
    7. 断网时明确提示“需要联网”；“我的 → 记录”仍可查看（本地缓存）。

    质量与成本

    • AI 输出用 JSON 模式，服务端用 zod 校验。校验失败重试 2 次，仍失败就标记“待重新生成”并告警。
    • 每张卡有“内容有误”按钮。点击后只重新生成这个学习单元。
    • 段落级记录只抽取 ≤ 3 个词或句型。材料里不出现段落原文。推断：工作文本不宜外传
    • 材料生成放在夜间批处理，不占用交互链路。花了知多少实测 DeepSeek 推理 token 占 85%，会挤占 max_tokens（heji-ledger WORKLOG.md），批处理要给足 token 预算。
    • 日均约 11 条记录。每天 1–3 次批量调用，加上手机端交互翻译，月成本预计每人低于 20 元。推断，M1 后按实际 token 复核

    6. 同步方案与架构

    选“阿里云 API + OSS”。小程序翻译本来就需要服务端代理 AI，同步服务正好承担这个角色。

    维度A. GitHub 私有仓库B. 纯 OSS（无服务端）C. 阿里云 API + OSS（选定）
    实现成本低：CLI 调 git 或 GitHub API低：CLI 上传 JSON中：要写一个服务
    小程序翻译做不到：key 不能放前端做不到：同上服务端代理 AI
    手机回写复习进度前端要持有 GitHub token，有泄漏风险要 STS 临时凭证，凭证仍需服务端签发原生支持
    AI 材料在哪里生成GitHub ActionsMac 本地（关机就不跑）服务器定时任务
    国内手机访问不稳定稳定稳定（备案域名）
    运维无无1 个容器；复用已有的 PostgreSQL 和 nginx
    结论：C 做主通道；OSS 存发音音频和每日备份；GitHub 只做可选的 Markdown 导出，导出结果可以直接放进 Obsidian。

    核心设计：只追加，不覆盖

    1. 原始记录不可变。记录由 CLI 或小程序产生，之后不修改。客户端生成 ULID，服务端按 ID 幂等写入。重复推送不会产生重复数据。
    2. 复习进度也只追加。每次评分写一条复习日志。卡片的调度状态由日志按时间重放得出（FSRS 是确定性算法）。两台设备离线复习同一张卡，两条日志都保留，不需要“后写者胜”。
    3. 游标用服务端自增序号。拉取游标是 seq，不是时间戳；推送和拉取的游标分开存。这条规避花了知多少的 P0-1 缺陷。那次 push 游标污染了 pull 水位线，拉取从此漏掉其它设备的数据（heji-ledger docs/21-发布验收报告.md）。
    4. CLI 先写本地，再推送。推送失败的记录留在待推送队列（Outbox），下次启动或产生下一条记录时重试。翻译流程不等同步服务。
    换成 PostgreSQL 后的序号坑：自增序列按分配顺序增长，不按提交顺序。两个写事务并发时，序号小的可能后提交，拉取方会永久跳过它。做法：账号表加一列计数器 last_seq，每次写入先执行 UPDATE users SET last_seq = last_seq + n WHERE id = $1 RETURNING last_seq 取号。这一行的行锁让同一账号的写入排队，序号顺序就等于提交顺序。AI 任务写卡片和材料时也用这个计数器。M1 用并发推送测试守住它。

    7. 账号体系

    按多用户设计，按邀请制运营。代价是每张表多一列 user_id；收益是以后开放给别人时不用重做。

    各端怎么登录

    端登录方式说明
    小程序wx.login 静默登录，服务端换取 openid 并绑定账号不用密码，用户无感
    CLI设备授权：终端显示二维码和 6 位码，在小程序里确认类似 gh auth login；CLI 不保存密码
    H5（可选）网页显示小程序码，微信扫码确认复用 CLI 的确认页
    管理员你的账号带 admin 角色；用服务端脚本生成邀请码不做管理后台

    S-->>C: access token + refresh token

    CLI 登录（设备授权流程）。CLI 只拿到属于你账号的令牌，从不接触密码。

    令牌与设备

    • 每台设备一对令牌：access token 有效 15 分钟；refresh token 有效 60 天。
    • refresh token 每次刷新都换新的，服务端只存哈希。有人重放旧令牌时，服务端吊销这台设备的整条令牌链。
    • “我的 → 账号与设备”列出全部设备，可以单独吊销。
    • CLI 把令牌存在 ~/.config/t-cli/auth.json，文件权限 600。

    数据隔离

    • 所有业务表都带 user_id；唯一约束也带上它，例如学习单元的 (user_id, type, norm_key)。
    • 仓储层（Repository）的每个方法都必须传入 user_id，不提供不带它的查询。
    • 自动化测试：用 A 账号的令牌请求 B 账号的数据，必须返回 404。
    • 限流和每日 AI token 预算都按账号计算。
    • 日志只记录 ID、长度和耗时，不记录用户输入的原文。
    • 可选加固：开启 PostgreSQL 行级安全（RLS），按会话变量 app.user_id 过滤。M1 先不开，越权测试稳定后再评估。

    11. 技术选型

    沿用花了知多少的 TypeScript 技术栈，复用服务器上已有的 PostgreSQL 和 nginx。不引入 Redis：邀请制规模一个进程就够。

    层选型理由
    代码组织t-cli 仓库改为 npm workspaces 多包结构：apps/cli、apps/server、apps/miniprogram、packages/coreprompt 需要两端共用。用 npm 而不是 pnpm：现有 7 个 CI 工作流都用 npm ci，不用改
    共享核心packages/core：prompt、语言检测、朗读文本提取CLI 和服务端用同一份 prompt
    CLI 同步客户端新增 sync.js 和 /sync 命令；用 Node 内置 fetch不加依赖；遵守 Ink 约束
    服务端Node 24 + Fastify + TypeScript + zod与花了知多少同栈，可复用 contracts 写法
    鉴权JWT（jose）+ 轮换的 refresh token；微信 code2Sessionaccess token 无状态校验；refresh token 只存哈希
    数据库PostgreSQL 16（服务器上已有的 Docker 实例）+ Drizzle ORM + postgres.js；新建数据库 tcli 和专用角色不多跑一个数据库进程；与花了知多少同版本、同驱动，迁移写法可复用
    数据库连接t-cli 容器加入花了知多少的 compose 网络，用服务名访问；5432 不对外；连接池上限 5；statement_timeout 5 秒实例的 max_connections 是 50，两个项目共用；核实时只用了 7 个 已核实（V1）
    词库搜索pg_trgm 模糊匹配官方镜像自带；中文分词插件不在官方镜像里
    定时任务进程内 cron；任务开始前取 pg_try_advisory_lock不需要 Redis / BullMQ；锁防止任务重复执行
    AIDeepSeek；沿用 LlmProvider 抽象；模型由 DEEPSEEK_MODEL 指定与 t-cli 当前配置一致
    小程序微信原生 + TypeScript + Skyline；流式用 enableChunked沿用花了知多少工程模板和体验版上传流水线
    语音输入微信同声传译插件花了知多少已在用
    复习调度ts-fsrsFSRS 的 TypeScript 实现；Anki 也用 FSRS
    发音服务端用 msedge-tts 生成 mp3，存 OSS，按文本哈希缓存t-cli 已在用 msedge-tts（src/tts.js:5）
    部署GitHub Actions 构建镜像，服务器只拉取；在已有 nginx 里加一个站点，证书沿用现有的 DNS-01 流程80 / 443 端口已由花了知多少的 nginx 占用，不能再起 Caddy；服务器内存小，不在上面构建
    备份扩展已有的 pg-backup.sh：每晚 pg_dump 一份 tcli 库，经内网端点传到 OSS，保留 30 天与花了知多少共用一套备份和状态检查
    测试集成测试在 CI 里起 postgres:16-alpine 服务容器序号并发、越权等测试要跑在真实 PostgreSQL 上
    可观测/healthz、/readyz（检查数据库连接）；AI 调用记录耗时和 token 数；任务失败发邮件告警告警渠道见 D11

    密钥全部走环境变量或阿里云 KMS，不进仓库。包括：DeepSeek key、数据库连接串 DATABASE_URL、OSS AccessKey、JWT 签名密钥、小程序 AppSecret。

    服务器内存紧张：这台 ECS 是 2 核 1.6 GB，另有 4 GB swap。2026-11-18 核实：系统已用 716 MB，可用 891 MB；5 个容器合计约 181 MB（api 80、worker 69、postgres 16、redis 9、nginx 6）。t-cli 服务设 mem_limit: 256m，Node 进程在同类负载下约占 87 MB，加上后仍有约 800 MB 可用。已核实（V1）
    注意：@t-cli/core 是私有包，不发布到 npm。npm run release:local 改由 scripts/release-local.mjs 打包：它把共享包放进 CLI 的 node_modules，用 bundleDependencies 一起打进安装包。直接对 apps/cli 执行 npm pack 得到的包装不上。

    13. 风险与应对

    最大的技术风险是小程序流式输出和首字延迟；最大的长期风险是正式发布的资质。

    风险影响应对
    首字延迟高手机翻译不顺手，回到其它工具M1 先实测；交互接口关闭推理或换模型；单词查询走短 prompt
    小程序流式分块乱码中文显示错字按字节拼接后解码；写单测覆盖“字节边界落在字符中间”的情况
    有人刷 AI 接口DeepSeek 额度耗尽设备 token；限流；输入长度上限；按天统计 token 并告警
    AI 释义或音标出错学到错误内容zod 校验；卡片“内容有误”一键重生成；M3 人工抽查
    工作文本上云泄露工作信息服务器自有；HTTPS；磁盘加密；OSS 私有桶；材料不引用段落原文
    越权读到他人数据隐私事故仓储层强制 user_id；越权自动化测试；日志不记原文
    令牌泄露他人冒用账号和 AI 额度access token 15 分钟；refresh token 轮换，重放即吊销；设备可单独吊销
    体验版人数上限邀请的人多了就用不了先核实上限（V4）；人数接近上限前决定是否正式发布
    同步游标缺陷拉取漏掉其它设备的数据服务端序号；推拉游标分开；序号按账号行锁取号，保证提交顺序；写并发回归测试
    与花了知多少共用数据库实例一方的慢查询或连接耗尽拖累另一方独立数据库和角色；连接池上限 5；statement_timeout；升级 PostgreSQL 时两个项目一起回归
    服务器内存不足容器被 OOM 杀掉每个容器设 mem_limit；镜像在 CI 构建；上线后看实测占用
    翻译方向误判系统把纯汉字的短日文译成英文点方向标签改为反方向，只影响本次
    正式发布资质体验版之外无法上线体验版阶段不受影响；需要公开时再核实类目和生成式 AI 资质
    复习负担过重坚持不下去每日新卡上限 15、复习上限 60，可调
    单人维护成本系统荒废单进程；复用已有的数据库、nginx 和备份脚本；不引入 Redis 和消息队列

    15. 术语表

    全文统一使用下列叫法。

    术语含义
    原始记录（Entry）一次翻译、纠错或查词的输入和输出，产生后不修改
    学习单元（Item）从原始记录抽取出的单词、句型或语法点；同一单元只存一份
    复习卡（Card）由学习单元生成的一张卡片，带调度状态
    复习日志（Review Log）一次评分的记录，只追加
    每日材料（Material）AI 每天生成的复习读物，含 6 个板块
    待推送队列（Outbox）CLI 本地还没有得到服务端确认的记录
    账号（User）一个使用者；所有业务数据都挂在账号下
    身份（Identity）账号的一种登录方式，目前只有微信 openid
    设备授权CLI 的登录方式：终端出码，小程序确认，CLI 拿到令牌
    AI 代理服务端替小程序调用 DeepSeek 的接口；key 只存在服务端
    体验版微信小程序的内测版本，不用提审，只有体验成员可用
    FSRSFree Spaced Repetition Scheduler，一种按记忆模型安排复习间隔的算法
    ULID按时间排序的唯一 ID，客户端即可生成，用于幂等写入
    序号（seq）服务端给每次写入分配的递增编号；客户端按它增量拉取
    tcli 库在已有 PostgreSQL 实例里为本项目新建的数据库
    方向标签翻译结果上方显示方向的小字，例如“中文 → 英文”；点它本次改为反方向
